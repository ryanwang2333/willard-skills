# diagnosing-bugs：有条理地排查难缠的 bug

当用户报告"坏了 / 报错 / 失灵 / 很慢"，尤其是盯代码盯不出来的疑难 bug 时，按下面的纪律走，**不要急着猜原因**。只有明确理由才可跳步。

## 第 1 步：先搭一个「反馈回路」（整个技能的核心）

先有一个**能稳定复现这个 bug、并能红绿分明判定**的测试/命令。没有它，盯着代码看一天也找不到根因；有了它，根因基本就是时间问题。

搭法（由易到难）：
- 写一个能触发 bug 的失败测试
- 用脚本（curl/命令行）对着运行中的程序发固定输入
- 把能复现的最小场景（一个函数调用、一小段数据）单独跑一遍
- 对"时好时坏"的：循环跑几百上千次，记录每次的输入/输出找规律

**回路要够紧**：更快（秒级）、信号更准（专测这个 bug 的特征）、更确定（同样输入次次触发）。

**搭不出来的情况**：坦诚说"这一步搭不出回路"，不要硬猜。请用户提供复现场景、权限或日志。

## 第 2 步：复现 + 最小化

跑回路确认它确实触发那个病根（而不是别的相近问题）。然后把场景**一步一刀**切到最小：减输入、减分支、减配置，每切一刀重跑，保留"仍能复现"的最小集合。

## 第 3 步：给假设排序

**先列 3–5 条可证伪的假设**（每条都要能说出"如果这是原因，那么改变 X 会让 bug 消失/加重"），排序后给用户过目再动手。用户常能一眼重排（"我们刚改过第 3 条"）。

## 第 4 步：求证

每次只改一个变元，对上一步的某条假设。优先"定点观察"（断点/看真实数据），而不是日志全打出来再 grep。给每条关键调试日志加唯一前缀（如 `[DBG-abc]`），排查完统一清除。性能问题：**先测量基线，再优化**，别先猜后测。

## 第 5 步：修复 + 回归验证

改之前尽量把最小复现写成**回归测试**（先让它红），再修复让它变绿，最后用第 1 步的原始回路整体跑一遍，确认病根确实消失。

## 第 6 步：扫尾 + 复盘

- 病根不再复现 ✔ 回归测试通过 ✔ 调试日志清掉 ✔ 临时脚本删掉 ✔ 根因结论写进提交说明
- 复盘一句："当初做什么能从根上防住这个问题？"（缺测试？结构埋雷？）有价值就建议补。
