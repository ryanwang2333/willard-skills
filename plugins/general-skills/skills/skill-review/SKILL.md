# skill 审查：能不能达到目标效果

**背景教训**：一个能力做成 skill 不等于它一定生效——skill 是按需加载的，只在触发时进入上下文；而内置工具（如 WebSearch）一直在上下文里，会被优先调用。曾因此出现"写了优先 WebFetch 的 skill，却还是先用了 WebSearch"的问题。

所以创建/修改 skill 前，先审查它是否真能达成目标。

## 前置决策：先判断"该用什么载体"

创建任何能力前，先问一句话：
**这个能力是"流程/方法"（按需才用），还是"强制规则"（每个会话都该生效）？**

| 情况 | 载体 | 原因 |
|---|---|---|
| 特定场景才用的流程（读图、review、排障） | skill | 按需加载，不占常驻 token |
| 想在每条会话都生效的强制规则 | **CLAUDE.md**（Global instructions） | 常驻加载，不会被内置抢跑 |
| 跨会话的事实/偏好 | 记忆 | 每次会话载入 |

## 逐条审查：这个 skill 能不能达成目标

1. **目标会漏触发吗？** 检查：能力如果被内置工具/行为抢先，skill 能拦住吗？若拦不住 → 核心规则应提到 CLAUDE.md，skill 只留细节。
2. **触发词够吗？** 描述里的触发词是否覆盖所有使用场景？太窄会漏、太宽会误触发。
3. **会不会被常驻规则抢跑？** 如果 CLAUDE.md 已有一条全局规则，skill 里的同内容属于重复——去掉，skill 只留细节，并标注"配合 CLAUDE.md"。
4. **信息是否最新/无重复？** frontmatter 是否只有一份？描述和正文是否一致（避免多份 metadata 打架）。
5. **边界是否清楚？** 与其他 skill（或 CLAUDE.md 常驻规则）是否有重叠；重叠时谁管什么。

## 输出

审查后明确说明：
- 这个能力**应该做成 skill、提进 CLAUDE.md、还是存记忆**，为什么。
- 若决定做 skill：让它管什么、CLAUDE.md 管什么、边界在哪。
- 若现有 skill 达不到目标：指出缺口，建议提进 CLAUDE.md 或修触发。

## 纪律

- 不为了有 skill 而做 skill；先想清楚载体对不对。
- 诚实评估：skill 做不到"强制生效"，这种期望本身就是设计错误，应改用 CLAUDE.md。
