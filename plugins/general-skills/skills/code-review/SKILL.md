# code-review：从「需求」和「规范」两个维度审代码

用户想审查一段代码或一处改动（自己写的或别人的）时，用两个**独立**维度分别审查，不要混成一份笼统的结论。

## 两个维度

- **需求轴（Spec）**：代码是否忠实实现了"用户最初要的那个功能"？有没有做错、漏做、或做了需求没要求的事（范围膨胀）？需求不明确时，按"它显然想完成的事"衡量，并注明未提供明确需求。
- **规范轴（Standards）**：代码本身干不干净、是否符合常规写法（对照下面的常见味道清单）。

一份改动可能"需求过了、规范挂了"，也可能反过来——所以两条轴**分开列**。

## 规范轴的常见味道清单

- **看不懂的名字**：名字看不出在做什么 → 改名
- **重复代码**：同样逻辑出现多次 → 抽共用
- **逻辑深陷他人数据**：方法总伸进别的对象拿数据 → 数据归属问题
- **参数/字段扎堆**：同几个值总结伴传 → 归成一个类
- **用原始类型表达概念**：字符串/数字/一坨 if-switch 硬表达一个领域概念 → 建类型或多态
- **一处改动散落多文件**：本可聚成一个模块的改得七零八落 → 聚拢
- **一个文件因多个无关理由被改** → 拆开
- **为猜想的未来做的抽象/参数** → 删掉，等真需要再加
- **为了对上实现的长调用链**（`.a().b().c()`）→ 在源头封装

## 过程

1. 确认审查范围（整个改动 / 某个文件 / 某个函数）。
2. 找到"需求来源"（用户原话、约定、issue；没有就按上述兜底）。
3. 两条轴**各查各的**，写清具体位置和问题，给出"最需要修"的优先级。
4. 呈现时两轴分开列，每轴给出最有价值的一条发现；不要只挑一个"最佳"盖过另一轴。
